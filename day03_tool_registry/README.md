# Day 3 · 工具注册表与异常兜底

> 一句话：Day 2 你学会了让模型调用工具；Day 3 你要解决**工具多了以后怎么不失控**。

## 一、这一天的核心命题

**工具的"说明书"和"实现"必须是同一份真相。**

Day 2 的写法是"两份清单"：写一个函数，再手写一段 JSON Schema。
工具只有 2 个时勉强能忍，代价是：

- 改参数名忘改 schema → 模型永远传错参数，且错误被包装成"系统异常"，模型以为是系统坏了
- 加参数忘改 schema → 这个参数永远没人用
- 描述写歪了 → 模型"以为"工具能做的事和它真能做的不是一回事，白白浪费步数

主项目 cs-agent 里工具会越来越多（订单、库存、工单、退款、物流……），
**双份清单必然烂**。注册表就是解药：`@tool` 一次登记，schema 由函数实时生成。

## 二、概念阶梯（三个台阶）

```
台阶一：登记        @tool 装饰器 —— 写函数即登记，菜单自动生成
        ↓
台阶二：校验        参数缺失 / 多余 / 类型不对 —— 全部拦在工具层，别让模型猜
        ↓
台阶三：兜底        异常分级：业务异常让模型自救，系统异常让模型停手
```

## 四、运行顺序


## 五、与 Day 2 的对照（差别只有一处）

| | Day 2 `step3_guardrails.py` | Day 3 `02_fc_with_registry.py` |
|---|---|---|
| 循环骨架 | `for step in range(max_steps)` | **完全一样** |
| 护栏①步数上限 | ✅ | **完全一样** |
| 护栏②同参去重 | ✅ | **完全一样**（改为每轮独立，源自 10.07 的 bug 修复） |
| 护栏③异常回传 | ✅（execute 内部 try/except） | ✅ → **升级为异常分级** |

**结论**：加一个工具，Day 2 要改两处（函数 + schema），Day 3 只写一个函数。

## 七、自测题（8 道）

1. `@tool` 为什么要把原函数原样 `return` 回去？（提示：不 return 会怎样？）
2. schema 里的参数类型是从哪来的？如果函数注解写成 `list[str]` 会怎样？
3. `required` 列表是怎么算出来的？一个有默认值的参数会不会进去？
4. 为什么"参数没有描述"要在**登记/生成 schema 时**报错，而不是在执行时报错？
5. 模型传 `{"quantity": "3"}`（字符串）给一个 `int` 参数，会发生什么？为什么这算容错而不是纵容？
6. `error_type=business` 和 `error_type=unexpected` 的区别是什么？为什么对模型的处理指示相反？
7. 如果 `execute_tool` 让异常直接抛出，Day 2 讲的哪条护栏就失效了？
8. 加第 6 个工具需要改几个文件、几行？——这题答对了，你就懂了注册表全部的价值。

## 八、面试可讲的三句话

- "工具层我做的是**单一事实来源**：schema 由函数签名和 docstring 自动生成，参数没写描述直接 fail fast——因为模型只能看到 description，没描述的参数等于没说明书。"
- "异常我做了**分级**：业务异常回传给模型让它自己纠正，系统异常也回传但明确告诉它别重试。错误本身是 Observation，会走路的信息。"
- "**加一个工具只写一个函数**——这是被 Day 2 那次'改漏 schema 导致工具失灵'的教训逼出来的设计。"

## 九、学习法（老规矩）

盲写一个最小 `@tool` → 用费曼方式给 JARVIS 讲一遍"为什么要有注册表"。
