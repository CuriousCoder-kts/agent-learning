- **操作**：依次跑 `step1_oneshot.py` 和 `step2_react.py`，只盯 S2（A1003 退款，已签收退实付 80%）。
- **记录**：
  - step1 的 S2 退款金额 = ？（模型心算 259×0.8 的结果）
  - step2 的 S2 退款金额 = ？（模型可调 calculator）
  - 两边的模型调用次数 / 步数 / 工具执行数。
- **预期**：step1 金额可能出错或含糊；step2 先查状态 → 查价格 → 再调 calculator，金额精确 207.2。
- **回答**：S1 和 S3 两边行为几乎一样——**那 ReAct 多花的 token 什么时候才值得？**（用"B 步参数依赖 A 步观察"造一个句子。）

## E2 · 提示词即策略：删掉系统提示里的策略句

- **操作**：`step2_react.py` 的 `SYSTEM_PROMPT`，把两句策略（"每一步先想清楚…"、"信息已足够就直接回答…"）删掉，只留第一句"你是电商客服助手…"。跑 S2。
- **预期**：步数或调用模式发生变化（可能变多变少、可能该停不停）——**决策模型的载体之一就在这几行字符串里**。
- **回答**：改的是 Python 逻辑吗？不是——那"策略"到底存在哪里？（对照 README 四载体表 ②。）

## E3 · 拆护栏②：注释掉 seen_calls 去重 ⭐必做

- **操作**：`step3_guardrails.py` 里把护栏②的 if 分支整个注释掉（`if signature in seen_calls:` 到 `else:` 前的那段）。跑 S4（三次要求查 A1002）。
- **预期**：模型每次"不放心"都真实执行查询——重复 Observation 反复入历史，token 白烧，还可能越问越糊涂。
- **回答**：护栏②拦下的每一次重复调用，省的是什么？（提示：API 是按 token 计费的，工具本身也可能是有副作用的写操作。）

## E4 · 制造错误观察：删掉依赖链的一环

- **操作**：`_tools.py` 的 `get_order_price` 里删掉 `"A1003"` 那一行数据。跑 `step3_guardrails.py` 的 S2。
- **预期**：模型查状态成功（A1003 已签收）→ 查价格拿到 error → **它不会崩溃也不会干瞪眼**，而是基于 error 想办法（改口/道歉/估算）。
- **回答**：这验证了护栏③的哪句话？（"错误也是信息"。再想一步：如果工具直接抛异常而不是返回 error 字典，step3 会怎样、step2 会怎样？）

## E5 · max_steps=1：把模型的自由掐到最小

- **操作**：新建临时文件 `exp_e5.py`（跑完删除）：
  ```python
  from step2_react import react_agent
  stats = react_agent(
      "帮我算一下订单 A1003 能退多少钱？规则：已签收只退实付的 80%。",
      max_steps=1,
  )
  print(stats)
  ```
- **预期**：第 1 步模型刚查完状态，循环就到顶了——返回"达到 max_steps，未收敛"。任务失败但**程序不崩**，失败被显式表达。
- **回答**：真实系统收到"未收敛"应该做什么？（提示：step3 末尾那句"此时应转人工"。这就是工程上的**降级路径**。）

## E6 · 污染说明书：把 calculator 描述改成"查天气" ⭐必做

- **操作**：`_tools.py` 里 calculator 的 description 改成 `"查询指定城市今天的天气情况。"`（参数描述不动）。跑 `step2_react.py` 的 S2。
- **预期**：模型面对金额计算却只有一本"天气预报说明书"——要么不敢调它、硬着头皮心算，要么调用得很别扭。S2 的答案质量大概率下降。
- **回答**：你改的是函数实现吗？没有——函数一个字没动。**那模型的行为为什么变了？**（四载体表 ③：description 是模型对工具的全部认知，它既是说明书，也是策略载体。）
